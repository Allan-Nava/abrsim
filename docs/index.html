abrsim

Your ladder is fine at 100 Mbps. What does it do on a train?

abrsim takes a real HLS ladder and a network trace, simulates what an ABR player would do, and reports what it cost the viewer — deterministically, offline, with no player and no traffic shaper.

zero dependencies byte-identical runs one static Go binary an audience, not one viewer
$ brew install --cask allan-nava/tap/abrsim

A cask, not a formula: the binary is prebuilt. macOS only — on purpose.

$ go install github.com/Allan-Nava/abrsim/cmd/abrsim@latest

Linux, macOS and Windows. No cgo, no ffmpeg, nothing to configure.

$ curl -LO https://github.com/Allan-Nava/abrsim/releases/latest/download/abrsim_linux_amd64.tar.gz

Six archives per release — linux, darwin and windows on amd64 and arm64 — with a checksums.txt beside them. Pick the exact names from the releases page; the version is in the filename.

one command, one answer
$ abrsim run https://cdn.example/master.m3u8 --trace mobile-4g --abr bola

                            ↳ visible as the picture repeatedly softening and sharpening

Three symptoms, one cause: the ladder jumps 6.2× between 360p and 1080p, so on a 3 Mbps cell the player is either stuck well below what the line can carry or reaching for a rung it cannot sustain — and it oscillates between the two.

The headline finding

The rung that does not exist

Not “you had stalls” — every tool tells you that. The seconds a viewer paid for a rung nobody encoded, and the bitrate it would have had.

It fires on evidence, not on shape. A hole in the ladder is only reported when the player actually sat below it: at least 15% of playback stuck there, and neighbouring rungs at least 1.8× apart for a WARN, 2.5× for a BAD. A ladder with a wide gap nothing ever fell into stays quiet, because nothing was lost.

How it works

Arithmetic, not a browser

abrsim never downloads the media. It reads the manifest, works out how big each segment is, and plays the whole session forward on arithmetic — which is why a 30-minute asset takes under a second and why two runs of the same inputs are byte-identical.

01

Read the ladder

Master and media playlists → rungs with bitrate, resolution, codecs and a segment list. Audio-only variants are not rungs.

02

Size the segments

EXT-X-BYTERANGE where it exists, else AVERAGE-BANDWIDTH × duration ÷ 8 — or one HEAD each under --sizes measured.

03

Play it forward

Buffer level, startup threshold, download time integrated from the trace, stalls when the buffer empties mid-download, a cap where the player stops requesting.

04

Judge the timeline

Seven checks over the per-request timeline, worst finding first, every measurement carrying its unit.

What one run actually produces

No clock

Nothing in a simulation path reads the time of day. Time is float64 seconds, never time.Duration: a nanosecond rounding on thousands of intervals accumulates into a drift the checks would report as a defect.

No random numbers

The built-in traces are generated from a fixed-seed integer hash rather than math/rand, whose stability across Go releases is not a promise worth resting reproducibility on.

No map iteration

Nothing that reaches the output is ordered by a Go map. Two runs are byte-identical, which is what makes a diff of two reports meaningful.

No network, during

The manifest is fetched once up front. The simulation itself touches nothing, so it runs in CI, offline, in parallel, at any speed.

Seven checks

Every check speaks on every run

A check that goes silent is indistinguishable from a check that passed, so each one reports even when there is nothing wrong. Severity is OK < WARN < BAD < ERROR, worst first — ERROR sorts above BAD on purpose: a check that could not run matters more than a defect you can already see.

switchesswitches/min How often did the rung change? Oscillation is usually the throughput estimate chasing noise, and it is visible as the picture repeatedly softening and sharpening. >4/min (WARN), >10/min (BAD)
efficiency% What was delivered against what the line offered, plus how much of the session sat below the top rung — the context that makes the percentage readable. sizes Were the byte counts measured, or derived from the manifest’s declared bitrate? A simulation reported as a measurement is the one way this tool could lie, so it says which it used, unprompted, in the output rather than in the docs. Never above OK — it is provenance, not a defect

A limit of this tool is never reported as a defect in the stream. A trace that ran out, a manifest format not yet read, a HEAD a CDN refused: each gets an honest OK or ERROR saying abrsim could not look — never a BAD that sends somebody hunting a phantom.

Network traces

Seven built-in networks, and yours

A trace is a piecewise-constant bandwidth function of time, and every chart below is drawn from the samples of the trace itself — steps, not curves, because a step is what the model integrates. The built-ins are generated from a fixed-seed hash, so they are byte-identical on every machine: a recorded trace checked into a repository is a binary fixture with a .csv extension. Each chart is scaled to its own peak, with the dashed line marking 5 Mbps in all of them — where that line sits is how the seven compare.

Before the first sample the first rate applies and after the last the last one holds: a recording is not a promise about the times it did not cover, and holding is the only extrapolation that invents no event. coverage tells you when a session outlived its trace by more than a quarter.

Three adaptation algorithms

Run the same ladder through more than one. Where they disagree, the difference is the estimator rather than the network — which is exactly the information a single algorithm cannot give you.

--abrDecides onFailure mode it is famous for
boladefault Buffer level, by Lyapunov optimisation (Spiteri et al., INFOCOM 2016), in the parametrisation dash.js ships — including the low-buffer throughput safeguard dash.js wraps around it. Without that safeguard it death-spirals on any ladder whose top rung is above the line: 59 stalls in 60 segments on an ordinary 3 Mbps cell.
throughput An EWMA of measured throughput times a safety factor: the highest rung that fits under it. Oscillation. It chases noise, and switches is the check that catches it.
buffer Buffer level alone, BBA-style reservoir and cushion. Slow to climb — but immune to throughput mis-estimation, which makes it the control group that tells you whether a stall was the network or the estimator.

Where an external authority exists, use it. BOLA’s parameters here are dash.js’s, not a derivation of our own. The first version solved the paper’s two requirements directly against the ladder — correct arithmetic, broken player: on a two-rung ladder those requirements pin the crossover at exactly the buffer cap, and finding it subtracts two numbers near 1.7e6 whose difference is near 6e-4. The answer carried six significant figures and the player never left the bottom rung. A two-rung ladder is not exotic here: it is what a stream with a hole in it looks like.

The CLI

Findings are output, not failure

The exit code is 0 whenever the simulation ran. Only --exit-on changes that, which is what makes it a gate rather than a thing someone runs after an incident.

abrsim run <master.m3u8> [flags]
  --trace NAME|PATH      built-in trace or a CSV (default mobile-4g)
  --abr NAME             throughput, buffer, bola (default bola)
  --sizes declared|measured
                         declared derives sizes from the manifest's bitrate;
                         measured spends one HEAD per segment for real byte counts
  --startup-buffer DUR   media buffered before playback begins (default 2s)
  --buffer-cap DUR       what the player holds before it stops requesting (default 30s)
  --play DUR             stop after this much media; 0 plays it all (default 0)
  --viewers N            simulate N people on variations of the same network and
                         report the spread instead of one session (default 1)
  --devices MIX          the screens that audience watches on, as
                         phone:50,tv:30,desktop:20 — shares must add up to 100
  --header 'K: V'        sent on every request; repeatable
  --timeout DUR          per-request timeout (default 30s)
  --json                 the full report, per-request timeline included
  --no-color             NO_COLOR is honoured too
  --exit-on LEVEL        exit non-zero at ok|warn|bad|error

Credentials go in --header values your shell reads from the environment — never into a flag that lands in shell history or a CI log. abrsim traces and abrsim algorithms list what is built in.

What --json gives a machine

The whole report, including the per-request timeline the checks are computed from — so a consumer never parses prose and can re-derive any figure itself.

As a CI gate on the encoding ladder
.github/workflows/ladder.yml
- run: go install github.com/Allan-Nava/abrsim/cmd/abrsim@latest
- run: |
    for t in mobile-4g train dsl-evening; do
      abrsim run "$LADDER_URL" --trace "$t" --abr bola --exit-on bad
    done

Three traces, three verdicts, no player and no shaper. The job fails only when a finding reaches BAD; everything below that is printed and passes. Add --json and keep the reports as artefacts if you want the timeline afterwards.

New in 0.3.0

An audience, not a viewer

One session over one trace is an anecdote — a true one, and still an anecdote. --viewers N simulates N people on variations of the same network and reports the spread, because the rung you are about to delete is defended or condemned by the tail of an audience rather than by its median.

Viewer 0 is the trace exactly as measured, and it froze for nothing at all. The single-viewer report on these same inputs says the stream is fine. At the 95th percentile of this audience the picture is frozen for a minute of the three and a half.

The same audience everywhere

Scales are stratified and permuted from the same fixed-seed hash the built-in traces use, so --viewers 500 is the same 500 viewers on any machine — and even --viewers 8 spans the range instead of being eight people on a good line.

Severity at a percentile

Every check carries its status at p50, p95 and p99, worst percentile first, and the checks are ordered by what happens at the p95. Each loud one says the percentile it starts firing from, and names the viewer with the worst case so you can go and look at that session.

The gate reads the tail

--exit-on judges the whole audience. One that read only the median viewer would pass a ladder that freezes for one person in twenty.

Stated, not hidden

A viewer's scale depends on how many viewers there are, so viewer 5 of 30 is not viewer 5 of 200. And the population --json carries the distribution plus a per-viewer summary, never two hundred request timelines.

Rung attribution

Seconds of the audience's playback each rung served, its share, how many viewers ever chose it. A rung nothing selected is named rather than dropped — it is exactly the one somebody is deciding about.

The units of a delivery bill

Bytes per viewer-hour, from the bytes that really crossed the wire. Dropping a rung becomes a number in both directions. No severity: what a gigabyte is worth is a commercial question.

The screen is part of the ladder

--devices phone:60,tv:40 — a screen does not fetch a rung it cannot show. Above, the phone half froze for nothing and cost 0.39 GiB an hour; the televisions froze a second and cost 0.64.

A score with its weights beside it

The literature's linear QoE in Mbps-equivalent: a 2.4 is worth a steady 2.4 Mbps with no stalls and no switching. The weights print with the score, and no severity is attached until our numbers are validated against published results.

Every figure is a viewer that existed. The percentiles are nearest-rank order statistics, never interpolated: an interpolated median of [1,2,3,4] is 2.5, which nobody in that audience experienced, and inventing a measurement is the one thing this tool must not do.

And a percentile the audience cannot support is not reported at all. A “p95” over ten viewers is the maximum wearing a better name, so a p95 needs 20 viewers and a p99 needs 100; below that the column is —, the report says what it would have needed, and the JSON says null. A limit of the audience is never dressed up as a limit of the stream.

Honest limits

What it does not model

Every one of these makes the simulation kinder to the stream than reality is, so the figures are a floor on the trouble rather than a ceiling. They are tracked backlog items, not omissions.

  • Request latency — no RTT or connection setup, so short CMAF segments look better than they are.
  • Audio sharing the connection — video gets the whole pipe.
  • A live edge — VOD semantics only; the buffer fills as fast as the line allows.
  • The startup rule a real player applies before BOLA — dash.js runs a throughput rule until playback is established, so the rung the first segment is fetched at is BOLA’s rather than a shipped player’s.
  • DASH — HLS for now.
  • Who the audience is — --devices takes a mix of screens, but abrsim will not invent one: with none stated, no screen is assumed. The population also varies in bandwidth alone — everyone starts at the same instant and watches the same asset to the end.

And unless you pass --sizes measured, a segment with no declared byte range is sized as AVERAGE-BANDWIDTH × duration ÷ 8, which is an estimate. Every report says which it used.

Planned work lives in BACKLOG.md with a stable AB-n id; ROADMAP.md is generated from it and CI fails when the two disagree.

Questions

The ones worth asking

Why not just run a real player behind a traffic shaper?

Because it is slow, not reproducible, and you cannot put it in a pipeline — so the question mostly does not get asked, and the ladder someone chose in 2019 stays where it is. abrsim answers it in a second, the same way twice.

Does it download the video?

No. It fetches the manifests, and with --sizes measured one HEAD per segment for real byte counts. The media itself is never transferred, which is what makes a 30-minute asset a sub-second run.

Then how does it know how big a segment is?

From EXT-X-BYTERANGE when the playlist declares it, otherwise from AVERAGE-BANDWIDTH × duration ÷ 8. The second is an estimate and travels as one: the sizes check says so on every run, and a HEAD the CDN refuses falls back to the estimate rather than failing the run.

Why does efficiency never say anything is wrong?

Because both attempts at a severity fired on healthy reference streams. Judging the whole session flags every stream watched on a line well above its ladder; judging only the playback below the top rung flags the ramp-up instead, since a buffer-based algorithm is always below the top while it climbs. Separating a slow ramp from real waste needs a definition of steady state, and until that exists the number is stated and the judgement is not made. A measurement with an honest “no opinion” beats a severity that cries wolf.

Is it a conformance checker?

Deliberately not. Segment bytes are segcheck’s job, manifests and fleets are checkfleet’s, and how a ladder was encoded is ladder-bench’s. abrsim only asks what a player does with what those tools describe.

Can I trust the numbers?

They are a floor, not a ceiling — see the limits above. Beyond that: the binary has no dependencies (go.mod has no require block and CI enforces it), every release is built from a tagged commit with a checksums.txt, and the reference-stream smoke test runs before a tag ships. Three of this project’s design errors were found by that smoke test and none of them by a unit test.
