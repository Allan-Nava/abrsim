abrsim

Your ladder is fine at 100 Mbps. What does it do on a train?

abrsim takes a real HLS ladder and a network trace, simulates what an ABR player would do, and reports what it cost the viewer — deterministically, offline, with no player and no traffic shaper.

zero dependencies deterministic one static Go binary exit 0 unless you ask otherwise
$ go install github.com/Allan-Nava/abrsim/cmd/abrsim@latest
$ abrsim run https://cdn.example/master.m3u8 --trace mobile-4g --abr bola

🔴 BAD    ladder-gap  360p..1080p      no rung between 360p and 1080p (6.2× apart): 116s of playback stuck on 360p while the line carried 2.9 Mbps
                            ↳ a rung near 2.6 Mbps would have been chosen for 48% of this session; the viewer watched 116s of it at 360p instead
🔴 BAD    rebuffer    mobile-4g        7 stalls, 17s frozen in 240s of playback (7.3%)
                            ↳ the picture is stopped for this long: it is the defect a viewer notices first and forgives least
🔴 BAD    switches    session          41 rung changes in 240s (10.2/min)
                            ↳ visible as the picture repeatedly softening and sharpening
🟢 OK     coverage    mobile-4g        240s of playback, entirely within the trace
🟢 OK     efficiency  session          2.5 Mbps delivered against 2.4 Mbps averaged over the session (104%)
🟢 OK     sizes       session          segment sizes are declared, not measured
🟢 OK     startup     session          1.1s to the first frame, starting on 360p

7 checks: 4 OK, 0 WARN, 3 BAD, 0 ERROR — 60 segments, 71.0 MiB, 240s of media in 250s over `mobile-4g` with bola, mean rung 2.5 Mbps

Three symptoms, one cause: the ladder jumps 6.2× between 360p and 1080p, so on a 3 Mbps cell the player is either stuck well below what the line can carry or reaching for a rung it cannot sustain — and it oscillates between the two.

The finding it exists for

Not “you had stalls”, but the rung that does not exist and the seconds a viewer paid for its absence.

Why it exists

The question is easy to ask and expensive to answer, so mostly it does not get asked.

To find out whether a ladder holds up on a bad connection you normally put a real player behind a traffic shaper and watch it. That is slow, not reproducible, and you cannot put it in a pipeline — so the ladder someone chose in 2019 stays where it is.

abrsim answers it in a second. It does not download the media: it reads the manifest, works out how big each segment is, and plays the whole session forward on arithmetic. Same inputs, same numbers, on every machine and every Go release — which is what makes it something you can gate a pipeline on.

It is deliberately not a conformance checker. Segment bytes are segcheck’s job, manifests and fleets are checkfleet’s, and how a ladder was encoded is ladder-bench’s. abrsim only asks what a player does with what those tools describe.

Checks

Seven, worst first. Severity is OK < WARN < BAD < ERROR.

CheckWhat it answers
ladder-gapWas the player stuck below a rung the line could carry, with nothing in between? Names both ends of the hole, the seconds lost, and the bitrate a rung there would have had.
rebufferHow long was the picture frozen, and how many times?
startupHow long before the first frame, and which rung was asked for first?
switchesHow often did the rung change per minute? Oscillation is the throughput estimate chasing noise.
efficiencyWhat was delivered against what the line offered. Reports a number, makes no judgement — both attempts at a severity fired on healthy streams.
sizesWere the byte counts measured, or derived from the manifest’s declared bitrate?
coverageDid the inputs cover the whole run — or did the trace run out, or the network die?

ERROR sorts above BAD on purpose: a check that could not run matters more than a defect you can already see. And a limit of this tool is never reported as a defect in the stream.

Network traces

--trace takes a built-in name or a CSV of seconds,bits_per_second. The built-ins are generated from a fixed-seed hash, so they are byte-identical everywhere: a recorded trace checked into a repository is a binary fixture with a .csv extension.

TraceWhat it is
flat-5m5 Mbps, unwavering. The control: any finding here is the ladder’s, not the network’s.
steps-downA staircase from 10 Mbps to 300 kbps, thirty seconds a step — makes the player visit every rung it has.
steps-upThe staircase in reverse: how long a player takes to climb back after the network recovers.
mobile-4g~3 Mbps with two collapses to 400 kbps. The everyday case, and the default.
train~6 Mbps between tunnels, nothing at all inside them. The trace no adaptation can save.
office-wifi20 Mbps with somebody else’s backup running.
dsl-evening8 Mbps degrading to 2.2 as the neighbourhood comes home, then recovering.

abrsim traces prints them with their spans.

Algorithms

Run the same ladder through more than one. Where they disagree, the difference is the estimator rather than the network.

--abrWhat it does
bolaLyapunov optimisation over buffer level (Spiteri et al., INFOCOM 2016) in the parametrisation dash.js ships, including the low-buffer throughput safeguard dash.js wraps around it — without which it death-spirals on any ladder whose top rung is above the line. The default.
throughputHighest rung under a smoothed estimate of measured throughput. The naive baseline, and the one that oscillates.
bufferBBA-style reservoir and cushion, on buffer level alone. Immune to throughput mis-estimation, slow to climb.

The CLI

Findings are output, not failure: the exit code is 0 whenever the simulation ran.

abrsim run <master.m3u8> [flags]

  --trace NAME|PATH      built-in trace or a CSV (default mobile-4g)
  --abr NAME             throughput, buffer, bola (default bola)
  --sizes declared|measured
                         declared derives sizes from the manifest's bitrate;
                         measured spends one HEAD per segment for real byte counts
  --startup-buffer DUR   media buffered before playback begins (default 2s)
  --buffer-cap DUR       what the player holds before it stops requesting (default 30s)
  --play DUR             stop after this much media; 0 plays it all (default 0)
  --header 'K: V'        sent on every request; repeatable
  --timeout DUR          per-request timeout (default 30s)
  --json                 the full report, per-request timeline included
  --no-color             NO_COLOR is honoured too
  --exit-on LEVEL        exit non-zero at ok|warn|bad|error

--exit-on bad is what turns it into a gate. --json carries the whole per-request timeline, so a machine consumer never parses prose. Credentials go in --header values your shell reads from the environment — never into a flag that lands in shell history or a CI log.

What it does not model

Every one of these makes the simulation kinder to the stream than reality is, so the figures are a floor on the trouble rather than a ceiling.

  • Request latency — no RTT or connection setup, so short CMAF segments look better than they are.
  • Audio sharing the connection — video gets the whole pipe.
  • A live edge — VOD semantics only; the buffer fills as fast as the line allows.
  • The startup rule a real player applies before BOLA — dash.js runs a throughput rule until playback is established, so the rung the first segment is fetched at is BOLA’s rather than a shipped player’s.
  • DASH — HLS for now.

And unless you pass --sizes measured, segment sizes are AVERAGE-BANDWIDTH × duration ÷ 8, which is an estimate. Every report says which it used, in the output rather than in the documentation: a simulation reported as a measurement is the one way this tool could lie.

Each limit is a tracked backlog item, not an omission — BACKLOG.md is the single source of truth for planned work and ROADMAP.md is generated from it.
